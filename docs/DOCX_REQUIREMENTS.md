## Current acceptance boundary

The current codebase can be deployed as a private daily-frequency research, backtest,
governance, automation, and paper-trading system, but the running installation is not
accepted merely because its containers are healthy. The **Tasks** page must report the
`research` profile as ready before research use and the `paper` profile as ready before
automated paper operation. At present, the active 2024-present download and its
verification/snapshot/Qlib/baseline stages remain real blockers. It is not a live-trading
system. Qlib and RD-Agent replace most research/backtest work that the document sketches
in C++. The separate `pair_research` profile additionally requires immutable minute bars,
daily shortability evidence, a successful native pair backtest, and a second-person
approved pair version. Pair strategies cannot enter the long-only paper ledger; the
dedicated atomic spread ledger is implemented, and `pair_paper` additionally requires
one scheduled ledger with at least five recent reviewed days and a clean risk/batch
state. The platform now owns provider-neutral TWAP/VWAP slicing and the fail-closed account
reconciliation loop and QMT provider-side execution state machine, but they do not
replace the broker-approved MiniQMT runtime or its real-time market feed.

Ordinary and pair-paper ledgers no longer need to remain forever on their creation-time
dataset. Each ledger explicitly chooses either an immutable pinned snapshot or the
latest verified compatible descendant. Automatic rollover requires the same stable
lineage and an append-only source-unit proof, and every scheduled batch persists the
exact Qlib identity and execution-manifest hash before a worker starts.

## Next operational acceptance order

1. Finish the active A-share initialization, then pass data verification, immutable
   snapshot, Qlib build and baseline stages until the `research` readiness profile is green.
2. Create and approve the first governed strategy, run at least five trading days of
   automatic paper rebalances/reviews, and pass the `paper` readiness profile.
3. Run the new `cn_margin_eligibility` and `pair_execution_1m` jobs with the real
   provider, inspect their immutable execution snapshot, pass `pair_research`, then run
   the dedicated two-leg spread ledger for five recent reviewed days until `pair_paper` passes.
4. Install the QMT gateway beside MiniQMT, provide a simulation account, and run the
   signed health/order/snapshot acceptance suite against the real provider runtime.
5. Run continuous paper-vs-QMT snapshot reconciliation, participation, partial-fill,
   disconnect, restart, duplicate-delivery, and stale-quote fault-injection drills.
6. Decide whether paid Level-2 order/trade queues add enough execution evidence beyond
   the implemented minute-bar and full-tick checks.
7. Run paper-vs-sandbox shadow trading, then require a separate user decision before
   any small-capital live adapter is added.
